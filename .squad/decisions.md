### 2026-08-25: Backend Clean Architecture Scaffold
**By:** Leia (Lead/Architect)

**What:** Scaffolded `/backend` as a .NET Clean Architecture solution (Domain -> Application -> Infrastructure -> Api) targeting **.NET 10** (`net10.0`), plus top-level monorepo layout (`/backend`, `/frontend`, `/infra`, `README.md`). Domain holds persistence-ignorant POCOs (`Well`, `ProductionRecord`, `Facility`); Application holds interfaces only (`IWellRepository`, `IProductionRecordRepository`, `IKpiService`, `ICsvImportService`) plus DTOs; Infrastructure references EF Core + SQL Server + ASP.NET Core Identity EF store with a skeleton `PetroVisorDbContext`; Api is ASP.NET Core Web API with Swashbuckle Swagger UI and only a `HealthController` initially. `PetroVisorLite.Application.Tests` (xUnit) added as a smoke-test harness.

**Why:** SQL Server chosen as EF Core provider since Azure SQL is the expected production target (swappable later without touching Domain/Application). .NET 10 used as the latest GA SDK available; no .NET 10-specific APIs used, so retargeting to .NET 8 LTS later is low-risk. No credentials committed — connection strings ship empty, with `dotnet user-secrets` for local dev and Managed Identity + Key Vault for Azure. Verified: `dotnet build` (0 errors/warnings, 5 projects) and `dotnet test` (1/1) both clean.

Networking left `publicNetworkAccess: 'Enabled'` (no VNet/Private Endpoint yet) to keep the scaffold deployable standalone — flagged in `infra/README.md` for production hardening, along with a note to reverify the `Microsoft.Sql` preview API version (`2023-08-01-preview`) against a confirmed GA version before real deployment.

### 2026-08-25: Backend Auth, Data, CSV Import & Seeding
**By:** Han (Backend Dev)

**What:** Built out Leia's scaffold into a working, locally runnable backend. Domain: `Well` gained `ArtificialLiftType`/`ArtificialLiftStatus` enums and a unique indexed `ApiNumber`; `ProductionRecord` gained `ChokeSize64th`, `WellheadPressurePsi`, and per-record lift type/status, with a composite unique index on `(WellId, Date)`. `PetroVisorDbContext` now extends `IdentityDbContext<ApplicationUser, IdentityRole, string>` (merged schema); `ApplicationUser` adds `DisplayName`; roles are `Engineer` (read/write) and `Viewer` (read-only). Auth: ASP.NET Core Identity + a custom `IJwtTokenService`/`JwtTokenService` issuing signed JWTs; `/api/auth/login`/`register` anonymous, everything else `[Authorize]`, writes additionally `[Authorize(Roles = "Engineer")]`. CSV import: `POST /api/production/import` (Engineer-only, 20MB limit) via CsvHelper, per-row validation with graceful defaulting on bad enum strings, returns `CsvImportResultDto`. Seeding: idempotent `SeedData.SeedAsync` (Development-only) creates 2 roles, 2 demo users, 2 facilities, 8 wells, ~6 months of daily production with a scripted lift-status change + correlated production drop on one well. Added `dotnet-ef` local tool, generated `InitialCreate` migration, and `PetroVisorLite.Api.Tests` (11 new tests: CSV import + auth/role enforcement via `WebApplicationFactory` + EF InMemory). **26/26 tests passing** total; `dotnet build` clean (0 warnings/errors, 7 projects); `dotnet run` verified `GET /api/health` returns 200.

**Why:** JWT signing key bound from `Jwt:Key` config (user-secrets locally, Key Vault + Managed Identity in Azure) — never hardcoded; falls back to a random per-process key (fail-closed) if unset rather than crashing at startup. Per-record lift type/status captured because lift state changes over a well's life, not just currently. Seed data deliberately scripts one well's lift-status change with a correlated production drop so Obi-Wan's loss/lift-monitor detectors and the frontend charts have a real signal to find. Could not verify migration/seeding against a real SQL Server in this macOS sandbox (no LocalDB, no running Docker daemon) — flagged for whoever has Docker/LocalDB to run `dotnet ef database update`.

### 2026-08-25: KPI/Analytics Service Implementation
**By:** Obi-Wan (Analytics Dev)

**What:** Implemented KPI/analytics logic in `PetroVisorLite.Application/Analytics/` as framework-agnostic interfaces operating purely on in-memory `IEnumerable<ProductionRecord>` (no EF Core/HTTP/persistence deps added). Added `IProductionKpiCalculator` (daily/monthly totals), `IDeclineRateCalculator` (exponential decline fit via OLS regression of ln(oil volume) vs. day-offset — the `b=0` case of Arps' equations), `IProductionLossDetector` (trailing rolling-average baseline, default 7-day window / 15% threshold), and `IArtificialLiftMonitor` (flags lift type/status changes and checks for a correlated production drop within a one-day lag). `IKpiService`/`KpiService` kept as Leia's stub, implemented as a thin orchestration facade calling `IProductionKpiCalculator`. Added `AddApplicationServices()` DI extension registering all five services. **15/15 tests passing** (1 pre-existing + 14 new); `dotnet build` clean for Application + Application.Tests in isolation.

**Why:** Each calculator kept deliberately simple with documented limitations (no hyperbolic/harmonic Arps curves, no ML-based anomaly detection, no population-level lift benchmarking) as an explicit, honest first approximation — the seams (`IDeclineRateCalculator`, `IProductionLossDetector`) are designed so a more sophisticated implementation (e.g. ML.NET) can be swapped in later without touching `KpiService` or its callers. Separate interfaces (rather than folding into `IKpiService`) since they operate over a well's full history, not a single query-shaped result.

### 2026-08-25: Frontend Pivot from React/npm to ASP.NET Core Razor Pages
**By:** Luke (Frontend Dev)

**What:** Abandoned the original React + TypeScript + Vite SPA plan after getting stuck for over an hour on npm package resolution (the corp machine's proxy, `packagefeedproxy.microsoft.io`, does not mirror all public packages the React toolchain needed). Per user (jasonfarrell) direction, pivoted to building `/frontend` as an **ASP.NET Core Razor Pages** app (`PetroVisorLite.Web`, `net10.0`, matching the backend) — no npm anywhere; only NuGet plus CDN-hosted Chart.js and Bootstrap 5 (with SRI hashes). All backend calls happen server-side via a typed `PetroVisorApiClient`. Auth bridges JWT to a cookie: `Login.cshtml.cs` posts to the backend, `JwtClaimsMapper` maps the login response into a `ClaimsPrincipal` (stashing the raw JWT under a private claim as a carrier), `SignInAsync` issues the ASP.NET Core auth cookie, and a `JwtForwardingHandler` `DelegatingHandler` reattaches the JWT to every outgoing backend call automatically. Pages built: Login, Logout, Wells/Index, Wells/Detail (Chart.js trend + KPI summary), Dashboard, Import (Engineer-only). Since the backend's `KpiController` only exposes production totals today, `Web/Analytics/ProductionTrendAnalyzer` implements lightweight client-side stopgap approximations of Obi-Wan's decline-rate/loss-detection logic. The original React attempt is preserved untouched at `/old-frontend` in case registry access improves later. 10/10 new tests passing; `dotnet build`/`dotnet test` clean; `dotnet run` verified via curl (`/Login`, `/`, `/Wells/Index` all 200, unauthenticated redirect to `/Login` works).

**Why:** NuGet works fine in this environment (verified via `dotnet restore` on a fresh scaffold) while the public npm registry does not — pivoting to a NuGet+CDN-only stack sidesteps the registry problem entirely rather than fighting proxy configuration. Server-side API calls (rather than client-side fetch) mean no client-side JS ever needs the backend base URL, API contracts, or auth tokens directly, keeping secrets and API shape off the browser. **Directive captured for future work:** on this corp/Microsoft machine, the public npm registry is unreachable — if a package can't be resolved, build without it; this applies to any future npm-based work in this repo. **Follow-up for Han/Obi-Wan:** expose decline-rate/loss-detection/lift-monitor as real KPI/analytics API endpoints so the frontend stopgap can be replaced with authoritative backend values. **Follow-up for Leia:** reconcile the top-level `README.md` frontend section (updated to describe `dotnet run` instead of `npm install`/`npm run dev`). **Follow-up for Lando:** `/frontend/PetroVisorLite.Web` needs its own Dockerfile/Bicep wiring when containerizing (the existing `frontend/Dockerfile`/`nginx.conf` target the abandoned React app and are now stale).

### 2026-08-25T17:49:32Z: Frontend Pivot #2 — Blazor WebAssembly (Static Web Apps compatibility)

**By:** Luke

**What:** Rebuilt `frontend/PetroVisorLite.Web` from the ASP.NET Core Razor Pages app (pivot #1) into a standalone Blazor WebAssembly app (net10.0), producing pure static output. Client-side JWT auth via `Blazored.LocalStorage` + a custom `JwtAuthenticationStateProvider`/`JwtParser`, bearer tokens attached via a `DelegatingHandler` on the typed API client. Chart.js integrated via JS interop (CDN script + `chartInterop.js` + `ChartInteropService`), replacing Razor Pages' server-side JSON serialization approach. All pages/components (Home, Login, Wells, WellDetail, Dashboard, Import) ported 1:1. bUnit + xUnit tests: 17/17 passing. `dotnet build`/`publish` verified clean; static output published to `frontend/PetroVisorLite.Web/bin/Release/net10.0/publish/wwwroot`.

**Why:** The user directed backend → Azure Container Apps, frontend → Azure Static Web Apps. Static Web Apps only serves static content (no persistent server process), which is incompatible with Razor Pages' cookie-auth/server-rendering model. Blazor WebAssembly compiles the whole app to static wasm/js/html, preserving the "no npm/node, C# frontend" constraint from pivot #1 while meeting Static Web Apps' static-hosting requirement. This is frontend pivot #2 overall: React (abandoned, npm registry blocked) → Razor Pages (pivot #1) → Blazor WebAssembly (pivot #2, final).

**Follow-ups:** `wasm-tools` workload not installed in this environment (non-AOT publish, larger bundle — optional future optimization). Backend still lacks a dedicated analytics endpoint, so decline-rate/loss-flag analytics remain an approximated client-side stopgap.
